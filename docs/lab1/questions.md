# ЛР 1: вопросы для ротации участников

Ответы относятся к текущему коду; оба участника должны уметь открыть указанный файл и показать механизм.

**Почему enkiTS, а не прежний пул?** Готовая библиотека разрешена ТЗ, простой собственный mutex-пул — нет. enkiTS даёт work stealing, приоритеты и диапазонные задачи. Наша обёртка добавляет lifecycle, handles, обработку исключений, зависимости и общую точку dispatch. Очередь loader больше не создаёт свои потоки. См. [JobSystem.cpp](../../engine/core/JobSystem.cpp).

**Сколько потоков и кто ими владеет?** Один `Application::m_jobs`; по умолчанию до четырёх workers. Главный поток тоже может исполнять задачи при ожидании. Это число workers нашего enkiTS-пула, не общее число OS-потоков процесса: Tracy, Diligent и драйвер могут создавать внутренние потоки. Renderer и ECS имеют не владеющие ссылки; renderer прекращает загрузки прежде, чем Application останавливает scheduler.

**Что делает work stealing?** Свободный worker может взять работу из очереди другого потока. Это механизм enkiTS, не наша реализация fibers. Задача не переносится между ядрами посреди функции по нашей инициативе; распределяются ещё не выполненные диапазоны/задачи.

**Чем `dispatch`, `parallelFor` и `dispatchAfter` отличаются?** Первый ставит одну функцию; второй делит диапазон и ожидает все его части; третий откладывает функцию до завершения предшественников. Handle относится к одному scheduler. `wait` не только ждёт, но может помочь выполнить допустимую работу и затем пробрасывает исключение.

**Может ли задача ждать ребёнка?** Да, ожидание кооперативное. Запрещено ждать себя или выполняющегося предка; shutdown/waitAll изнутри задачи тоже запрещены. Проверки и тесты — [JobSystemTests.cpp](../../tests/JobSystemTests.cpp). Это не поддержка произвольных циклических графов.

**Что происходит при исключении decoder?** `AsyncLoadQueue` ловит его в worker и сохраняет `exception_ptr` в заранее созданном completion. Главный поток получает ошибку, переводит ресурс в `Failed` через callback; loader/renderer продолжают работу с placeholder. Исключение GPU-finalization обрабатывается там же, на главном потоке.

**Где гарантия видимости CPU-данных?** Worker завершает запись, делает `ready.store(true, release)`. Pump читает `ready.load(acquire)` и только затем использует результат. Сами deque принадлежат главному потоку; workers их не изменяют. См. [async_load_queue.cpp](../../engine/resources/async_load_queue.cpp).

**Почему GPU upload теперь можно выполнять в worker?** Добавлен отдельный Diligent transfer context и настоящий GPU fence для D3D12/Vulkan. Jobs записывают copies под mutex, main только опрашивает fence и публикует handles после GPU completion. Workers не используют graphics context. На неподдерживаемом backend/adapter и при TGE_GPU_UPLOAD=0 — прежний main pump. [Подробности](gpu-upload-queue.md).

**2 мс — строгая верхняя граница кадра?** Нет. Это условие прекратить запуск следующих финализаций; один драйверный upload не прерывается и может длиться дольше. Есть дополнительный лимит одного ресурса на кадр. Зону pump и худший кадр нужно смотреть в Tracy.

**Почему ограничено число запущенных загрузок?** Максимум `min(2 × workers, 16)` running/decoded ресурсов. Это удерживает CPU staging memory и не даёт переполнить pipe, при котором enkiTS мог бы выполнить dispatch inline. Это лимит ресурсов, не мегабайт; очень большой ресурс всё ещё потребляет много памяти.

**Что происходит при выходе с загрузкой?** Новые запросы запрещены; backlog не запускается. Уже отправленные задачи join-ятся, их GPU-completion отменяются с сообщением. Renderer/GPU уничтожаются после join, общий scheduler — последним. Принудительное прерывание Assimp/stb в середине вызова не используется.

**Почему задача №2 — render matrices, а не физика?** Она уже нужна каждому render-объекту, работает с текущей ECS на hash-таблицах и остаётся полезной после физического middleware в будущей лабораторной. Физические stages — дополнительные пользователи общего scheduler.

**Snapshot делает весь World thread-safe?** Нет. Snapshot фиксирует список entity ID. Workers ещё читают Transform и Hierarchy из `const World`; изменение/rehash/удаление во время batch запрещены фазой движка. Каждый worker пишет только свой диапазон выходных матриц. GPU submit начинается после join. См. [transform_batch.h](../../engine/ecs/transform_batch.h).

**Почему нельзя одновременно запустить update и render preparation?** Update пишет Transform/Hierarchy, которые читает preparation: возникнет read/write-конфликт. Текущий порядок — закончить update, gather, параллельная read-only фаза, join, submit. Универсальный детектор read/write-конфликтов не реализован и не заявляется.

**Зачем threshold 1024 и grain 256?** Dispatch, учёт завершения и синхронизация имеют стоимость. Для маленького массива остаётся последовательный путь. Для большого — диапазоны по нескольку сотен объектов дают полезную работу на задачу. Это настройка текущего CPU/workload, не универсальная константа.

**Как проверена правильность результата?** Тест матриц строит 4096 объектов с иерархиями, сравнивает serial, parallel и прямой `computeWorldMatrix` с допуском `1e-5`. Отдельно проверяются пустой batch и несовпадение размеров. Тесты loader проверяют main-thread finalization, лимиты count/time, ошибки, 1024 mixed jobs, выход и перезапуск. Успешный статус брать из фактического CTest-лога.

**Что означает before при уже существовавшем async?** Исходник действительно имел свой пул из четырёх workers. Синхронный before — управляемое отключение async в том же бинарнике. Отдельный `legacy-pump` имитирует старый drain без лимита, сохраняя новый scheduler. Нельзя выдавать эти режимы за измерение старого commit.

**Как исключается прогрев и сравниваются прогоны?** Release+Tracy, одна сцена/камера/разрешение, первые три секунды исключены, N≥3 на режим. Порядок AB/BA меняется. Каждый trace выравнивается по `LAB_RUN_START`; median/p95/p99 сначала считаются внутри прогона, затем агрегируются по прогонам. Скрипт сохраняет executable SHA-256 и fixture manifest.

**Почему нет такого же ускорения FPS, как у зоны?** Остальные стадии кадра остаются последовательными или ограничены GPU. Уменьшение одной зоны ограничено её долей в кадре. Также scheduler и Tracy имеют накладные расходы. Показываем отдельно wall time зоны и полный `Main Frame`.

**Почему требовалось увеличить descriptor heap?** На D3D12 сцена с 4096 draw-объектами превысила стандартный динамический лимит Diligent 8192: фактический пик после исправления — 8704 дескриптора. Они нужны для привязки GPU-ресурсов и остаются заняты до завершения работы GPU. В `DiligentDevice.cpp` установлен размер 262144 с запасом. Это условие стабильной отрисовки большой сцены; настройка одинакова в before/after и не засчитывается как ускорение задач. Ошибочная первичная серия `release-final` — диагностическая; актуальная серия — `release-verified`.

**Что значат p95/p99 и почему недостаточно среднего?** Это значения, ниже которых лежат 95%/99% наблюдений. Редкие фризы могут почти не изменить среднее. Для загрузки дополнительно нужны max и локальное окно вокруг `LAB_LOAD_START`, потому что единичный длинный кадр иногда не попадает даже в p99.

**Можно ли суммировать worker time для времени кадра?** Нет: задачи выполняются одновременно. Для задержки нужна охватывающая main-зона и `Main Frame`; суммы worker time описывают CPU work, а не elapsed time.

**Какие ограничения остались?** Нет L2 streaming-пула, fibers и runtime read/write-analyzer. Copy queue есть для D3D12/Vulkan с transfer-capable adapter; ready-handle publication остаётся main-thread. Shader manifest фоновый, компиляция/чтение source в Diligent пока main. Приоритеты не прерывают decoder; shutdown ждёт библиотечного IO и GPU uploads.
