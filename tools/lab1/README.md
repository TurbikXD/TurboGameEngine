# ЛР 1: ресурсы, замеры и стабильность

Допфича upload queue: [архитектура и защита](../../docs/lab1/gpu-upload-queue.md). Запуск A/B: `Invoke-Lab1Measurements.ps1 -Scene loading -CompareGpuUpload -Runs 3`; живое демо: `Launch-Lab1Demo.ps1 -Scene loading -Mode after -GpuUpload -Tracy`. Обычный runner явно отключает transfer queue, сохраняя исходную методику L1; отдельный флаг сравнивает main upload и transfer при async decode в обоих режимах.

Нужны Windows PowerShell, Node.js (без npm-пакетов), Release-приложение с Tracy 0.13.1 и инструменты той же версии.

```powershell
cmake --preset profile-release
cmake --build --preset profile-release --target app
.\tools\lab1\New-BenchmarkAssets.ps1
.\tools\lab1\Invoke-Lab1Measurements.ps1 -Scene all -Runs 3 -IncludeUnboundedPump -OutputDirectory reports\lab1\release-verified
.\tools\lab1\Invoke-Lab1Stress.ps1
```

Пути по умолчанию: приложение `C:\tge\profile\Release\app.exe`, Tracy `C:\tge\tracy-0.13.1`, ресурсы `C:\tge\lab1-assets`. Все задаются параметрами. Результаты — в новом каталоге `reports/lab1/<timestamp>`; старые данные не перезаписываются.

Генератор создаёт 12 настоящих RGBA PNG 2048×2048 и 4 OBJ-поверхности по 131072 треугольника. Чтение, декодирование, парсинг и GPU-загрузка выполняются штатными загрузчиками движка. SHA-256 и параметры сохраняются в `manifest.json`; повторный запуск проверяет неизменность. Для быстрой проверки можно создать отдельный набор `-TextureSize 64 -MeshGrid 8 -OutputDirectory C:\tge\lab1-assets-small`; использовать его для итогового сравнения не следует.

Runner выполняет отдельные эксперименты `ecs` и `loading`, по 3 запуска before и after. Меняется только переключатель изучаемой функции: `TGE_JOBS` или `TGE_ASYNC_LOADING`. Порядок AB/BA чередуется. Каждый процесс сам закрывается через `TGE_DEMO_SECONDS=18`; успешное завершение не имитируется принудительным убийством процесса. При таймауте runner останавливается и сообщает PID.

В исходной версии уже был собственный пул async-загрузки на 4 потока. `loading/before` — контролируемое отключение async, демонстрирующее L1, а не описание исходной реализации. `loading/after` использует общую job system и GPU-памп с лимитами 1 ресурс/кадр и 2 мс. Опция `-IncludeUnboundedPump` добавляет ещё N прогонов `legacy-pump`: общий новый scheduler сохраняется, а лимиты пампа увеличиваются до 65536 ресурсов/60000 мс, чтобы отдельно измерить эффект ограничения финализаций. Это эмуляция прежнего неограниченного drain, не старый бинарник. Для трёх режимов порядок циклически меняется между повторами.

Приложение сначала завершает инициализацию и пишет `LAB_READY_FOR_TRACY`. Runner подключает capture; `TGE_WAIT_FOR_TRACY=1` задерживает начало цикла до подключения, позволяя сохранить `LAB_RUN_START`. Первые 3 секунды после него — прогрев. CSV экспортируется в исходном виде (`-u`, `-m`). Основной диапазон +3…+14 секунд одинаков для всех прогонов, загрузка начинается на +6 секунде. Дополнительное окно загрузки −1…+5 секунд относительно `LAB_LOAD_START` содержит событие и последующие кадры. Если маркер или полное окно отсутствуют, анализ завершается ошибкой.

`measurements.md`, `summary.json`, `per-run.csv`, `aggregate.csv` создаются только из записанных трейсов. Кадровые квантили рассчитываются отдельно по каждому прогону; итог — медиана метрик прогонов. Отдельные кадры не считаются независимыми испытаниями. Сохранены также max, число полных зон и отбрасывание граничных/незавершённых зон. Worker-time нельзя суммировать и выдавать за frame wall time.

`runs.json` фиксирует CPU, физические/логические ядра, RAM, ОС, обнаруженные GPU/драйверы, выбранные параметры соседнего CMake cache и SHA-256 приложения. Фактическое число workers берётся отдельно из журнала каждого запуска. Смена бинарника между прогонами останавливает эксперимент. Наличие текущего git revision в контексте не выдаётся за доказательство происхождения бинарника.

Для повторного анализа без новых запусков:

```powershell
node .\tools\lab1\analyze-traces.mjs .\reports\lab1\<timestamp>\runs.json
```

Stress проверяет отсутствующие ресурсы, автоматический выход сразу после начала загрузки, длительную сессию и повторные старты. Кроме нулевого кода завершения необходим `Application shutdown complete`; ранний выход принимается только при `LAB_SHUTDOWN pending_cpu=N pending_uploads=N` с суммой >0. В штатных сценариях загрузка должна завершиться с ≥16 готовыми ресурсами без ошибок/отмен.

## Живое демо

```powershell
.\tools\lab1\Launch-Lab1Demo.ps1 -Scene loading -Mode before -Seconds 30
.\tools\lab1\Launch-Lab1Demo.ps1 -Scene loading -Mode after -Seconds 60
.\tools\lab1\Launch-Lab1Demo.ps1 -Scene ecs -Mode after -Seconds 60 -Tracy
```

Команды запускаются по очереди после закрытия предыдущего окна. Launcher открывает видимое приложение; по умолчанию ожидание профилировщика выключено. С `-Tracy` заранее откройте GUI Tracy 0.13.1 и сразу подключитесь к `127.0.0.1`: после инициализации движок ждёт подключения до 10 секунд. Загрузка начинается на +6 секунде, приложение закрывается само через заданное время. Окружение текущей PowerShell-сессии восстанавливается сразу после старта дочернего процесса. Launcher не запускает второй экземпляр при активном замере.

## Сравнение количества workers

[Результаты 4 vs 24 от 09.10.2026](../../docs/lab1/workers-4-vs-24.md): 12 настоящих трейсов, условия эксперимента и ограничения.

```powershell
.\tools\lab1\Invoke-Lab1Measurements.ps1 -Scene all -CompareWorkers -BeforeWorkers 4 -AfterWorkers 24 -Runs 3
# Живое демо с 24 workers и тем же контролируемым лимитом ресурсов:
.\tools\lab1\Launch-Lab1Demo.ps1 -Scene loading -Mode after -GpuUpload -Workers 24 -AssetInFlight 16 -Tracy
```

Это самостоятельный A/B: в **обоих** режимах включены jobs, async decode и transfer queue. Меняется только размер общего CPU-пула. Before/after здесь означают 4/24 workers, а не отключение jobs/async/upload. Asset in-flight limit фиксирован на 16 (параметр -WorkerComparisonInFlight), иначе он автоматически менялся бы вместе с workers. Публикация остаётся 1 ресурс/кадр и 2 мс. Runner проверяет реальные workers и in-flight по LAB_RUN_START, активную transfer queue и успешную загрузку всех 16 ресурсов; анализатор отвергает несовпадающие настройки. Старые результаты не смешиваются с новой серией.

Обычный app читает `TGE_JOB_WORKERS` при создании Application: 1…256 — явный размер пула; 0/пустое/невалидное значение — прежний auto с максимумом 4. `TGE_ASSET_IN_FLIGHT`: 1…16 — фиксированный лимит, 0/пустое/невалидное — прежний min(2×workers,16). Переменные меняются только для запускаемого процесса, настройки Windows не меняются. Значение 24 само по себе не меняет постоянный дефолт.
